# Phase 2 — Vehicle management

Vehicle management builds on the existing authenticated application, customer CRUD and persistent D1 schema. No customers, vehicles or work history are seeded.

## Workflows

| URL | Behavior |
|---|---|
| `/vehicles` | Search, customer/manufacturer/size/year filters, sorting and server pagination |
| `/vehicles/new` | Register a vehicle against an existing customer |
| `/vehicles/new?customerId=UUID` | Register a vehicle with its customer preselected |
| `/vehicles/[id]` | Vehicle information, owner contact details and real work-order history |
| `/vehicles/[id]/edit` | Update information with optimistic concurrency protection |
| `/customers/[id]` | Owned vehicles link to their detail pages; an add action starts the preselected-customer workflow |

The customer selector supports search and pagination, so selection is not limited to the first page of customers. Manufacturer suggestions come from actual stored records and allow free text. Empty states and errors explain missing customers and unavailable data.

## Data and rules

- IDs are UUIDs generated by the server. Creation/update timestamps and a row version are returned by the API.
- Customer, manufacturer and model are required. A customer must exist in the authenticated business.
- Production year is optional: a whole year from 1886 through the next model year.
- Registration is optional, trimmed and uppercased, with a 20-character limit. No country-specific plate format is imposed.
- Color is optional (80 characters). Manufacturer and model are limited to 100 and 120 characters.
- Size categories are `small`, `medium`, `large`, `extra_large`; the editable initial selection is `medium`.
- Notes are optional plain text, with a 10,000-character limit.
- Unknown input fields and client-supplied business IDs are rejected. Owner access is checked on every endpoint.

Foreign keys enforce that every vehicle belongs to one customer in the same business. Customers with vehicles cannot be deleted. A vehicle without work orders may be reassigned to another customer in the same business; both customer detail pages then reflect the change. Once work orders exist, changing the owner or deleting the vehicle is blocked to preserve history. Other vehicle information may still be edited. Stale edits/deletes return a conflict and never overwrite newer data.

Search covers manufacturer, model, registration, color and owner name, with Hungarian accent folding and literal treatment of SQL wildcard characters. Registration searches ignore common spaces, periods and hyphens. Filter values and sort choices are validated; all user values are bound SQL parameters.

## Service history

The detail page reads actual work orders and their recorded service-name snapshots. It displays real job status and dates, with ten records per page. It does not invent example jobs, calculate spending, or implement work-order creation. Work-order management remains the next phase.

## API

| Method | Endpoint | Result |
|---|---|---|
| GET | `/api/vehicles?q=&customerId=&manufacturer=&sizeCategory=&productionYear=&sort=vehicle_asc&page=1&pageSize=20` | Paginated vehicles and their customer summaries |
| POST | `/api/vehicles` | `201 {vehicle}` with a detail `Location` header |
| GET | `/api/vehicles/[id]?historyPage=1` | `{vehicle,customer,serviceHistory}` |
| PUT | `/api/vehicles/[id]` | `200 {vehicle}`; body includes editable fields and expected `version` |
| DELETE | `/api/vehicles/[id]` | `204`; body is `{version}` |

Validation returns 422; missing vehicles return 404; linked history and stale versions return 409. Responses are private/no-store. Mutations require same-origin JSON and bounded request bodies. Internal exception text is not returned.

## Migration

Append `drizzle/0002_vehicle_management.sql` after the existing two migrations. It adds a constant-default version column and indexes without changing existing vehicle IDs, ownership or timestamps. Existing migration files and journal entries remain unchanged.

For an already migrated Phase 1 local database, build the Worker and apply only the new migration:

```sh
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0002_vehicle_management.sql
```

A fresh database needs all numbered migrations, in order. Sites packages the migration directory and applies pending migrations at publication.

## Verification

Run `node --test tests/*.test.mjs` (or `npm test`) for the complete foundation/customer/vehicle integration suite. Coverage includes ownership and orphan prevention, customer pages, reassignment and deletion protection, service-history snapshots and pagination, filters, search, persistence after reopening, migration preservation, authorization, bounded input and stale changes.

The combined suite has 64 passing tests locally and in [GitHub Actions](https://github.com/Jojolildog/Detailingdrive/actions/runs/43747729162). Dependency installation, UI type checking and the production Worker build passed for Phases 1–2. Browser QA and hosted D1 verification remain outstanding.
