# Customer management

Customer management extends the authenticated Phase 0 application. It uses the existing D1 customer and vehicle tables and adds an optimistic-concurrency version column through an append-only migration.

## Workflows

| URL | Behavior |
|---|---|
| `/customers` | Customer list, name/phone/email search, name or newest-first sorting, and server pagination |
| `/customers/new` | Create a customer with required name and phone, optional email and notes |
| `/customers/[id]` | Contact details, notes, creation date, and actual registered vehicles |
| `/customers/[id]/edit` | Edit customer details while retaining the original creation date |

Both the list and detail pages provide deletion confirmation. A customer with registered vehicles or work orders cannot be deleted. The application preserves linked data and returns an explanatory conflict response. Job history and total spending remain explicitly marked for a future phase; no values are fabricated.

The interface supports Hungarian and English, light/dark appearance, keyboard operation, mobile layouts, unsaved-change prompts and error states. These preserve the existing shell and settings behavior.

## Data and validation

- `fullName`: required, trimmed, NFC-normalized, at most 160 characters, no control characters.
- `phoneNumber`: required, at most 40 characters, containing 6–20 digits and ordinary international/domestic formatting.
- `email`: optional, trimmed, at most 254 characters, checked when supplied; blank becomes `null`.
- `notes`: optional, at most 10,000 characters, displayed as plain text.
- `id` and `createdDate`: generated by the server. The creation date cannot be edited.
- `version`: returned by the API; required for edits/deletion to prevent stale changes.

The server accepts only the documented input fields. Every query uses the authenticated business ID, and request bodies cannot select another business. Writes require same-origin JSON. Requests are bounded, SQL parameters are bound, pagination and sorts are validated, and responses are private/no-store.

Search folds Hungarian accents and case, supports multiple search terms, and normalizes common phone formatting. SQL wildcard characters in user searches are treated literally. Names use accent-folded ordering with an ID tiebreaker. This is deterministic accent-insensitive ordering, not a complete implementation of Hungarian linguistic digraph collation.

## API

| Method | Endpoint | Result |
|---|---|---|
| GET | `/api/customers?q=&sort=name_asc&page=1&pageSize=20` | `{items,total,page,pageSize,totalPages,query,sort}` |
| POST | `/api/customers` | `201 {customer}` and a detail `Location` header |
| GET | `/api/customers/[id]` | `{customer,vehicles}` |
| PUT | `/api/customers/[id]` | `200 {customer}`; body contains customer fields and expected `version` |
| DELETE | `/api/customers/[id]` | `204`; body is `{version}` |

Validation returns 422; missing records return 404; linked records or stale versions return 409. Internal database errors are not exposed.

## Migration and verification

Preserve `0000_foundation.sql` unchanged. Apply the new `0001_customer_management.sql` once to each existing database. For a fresh database, apply both in order. Sites publication packages the SQL migration journal and applies pending migrations.

For a local preview, after building the Worker:

```sh
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0001_customer_management.sql
```

Run `npm test` (or `node --test tests/*.test.mjs`) for repository and API integration checks, including reopening the SQLite database, preserving existing rows through migration, search/sorting/pagination, access boundaries, stale edits and protected deletions. Then run `npm run typecheck` and `npm run build` in an environment with the locked dependencies installed. Browser and hosted D1 acceptance checks remain necessary before calling the feature live.
